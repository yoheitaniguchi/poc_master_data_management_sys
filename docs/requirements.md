# マスタ管理システム PoC 要求仕様書（ClaudeCode向け）

## 0. 本ドキュメントの位置づけ

本ドキュメントは、マスタ管理システムのPoC（Proof of Concept）実装をClaudeCodeに依頼するための要求仕様書である。目的は「仕様検討の深掘り」であり、アーキテクチャは意図的に簡易な構成を選定している。実装時は本書の「やらない事」を遵守し、スコープ外の機能を追加実装しないこと。

---

## 1. 目的・効果

### 1.1 目的

| ID | 目的 |
|----|------|
| PURPOSE-1 | JSON定義駆動型アーキテクチャ（マスタ定義・バリデーション・連携ファイル仕様をJSONで外部化する設計）の技術的実現可能性を検証する |
| PURPOSE-2 | 将来の本番システム（Java/Spring Boot構成）への移行を見据え、仕様の詳細をPoCの実装・動作確認を通じて確定させる |

### 1.2 効果（実装時の判断基準）

以下は実装が要求を満たしているかを判断する基準であり、実装方針に迷った場合はこれを優先する。

| ID | 効果基準 | 判定方法 |
|----|---------|---------|
| EFFECT-1 | JSON定義ファイルの追加のみで、新規マスタテーブルをコード修正なしに追加できる | `table-definitions/` に新しい定義JSONを1つ追加し、アプリを再起動（リロード）するだけで、取込・検索・出力の各画面に新テーブルが反映されることを確認する |
| EFFECT-2 | バリデーション・整合性チェックの「値」（長さ、定数リストの中身等）がJSON定義の変更だけで拡張できる | 既存カラムの `maxLength` や `constants` の値をJSON上で変更し、コード修正なしに新しい制約でCSV取込が動作することを確認する |

**注記（重要）**: EFFECT-2はバリデーション**ルールの値**の変更を指す。新しい種類のルール（例: 正規表現パターンチェックのような、現在のJSONスキーマに存在しない検証方式）を追加する場合は、バリデーションエンジン自体のコード修正が必要であり、これはJSON変更のみでは対応できない。本PoCではこの制約を許容する。

## 4. 前提とするアーキテクチャ

- **ホスティング**: GitHub Pages（静的ファイルホスティングのみ）
- **データ永続化**: ブラウザのIndexedDB（サーバー不要、ユーザーのブラウザローカルに閉じる）
- **非同期処理**: Web Worker（メインスレッドをブロックしないCSVパース・バリデーション処理）
- **DAO生成タイミング**: 実行時生成（アプリ起動時にJSON定義をfetchし動的にIndexedDBスキーマとアクセス関数を構築する）
  - 採用理由: JSON定義の差し替えだけでテストケースを増やせるため、自動テストによる品質確保のサイクルを高速に回せる。デプロイ時生成（ビルド時にコード生成）は型チェックの利点があるが、JSON定義変更のたびにビルドが必要になりPoCでの検証速度が落ちるため不採用とした。

### 4.1 データフロー概要

```
[起動時]
table-definitions/*.json ──fetch──> DAO生成ロジック ──> IndexedDBスキーマ構築

[取込時]
CSVファイル ──> Web Worker
                  ├─ パース
                  ├─ バリデーション（テーブル定義JSONを参照）
                  │    ├─ 正常行 ──> IndexedDBへUpsert登録
                  │    └─ エラー行 ──> スキップ（登録しない）
                  └─ 取込ログ生成（import_logsストアへ記録）

[検索・出力時]
検索画面 ──> IndexedDB検索 ──> 一覧表示
                              ├─ CSVダウンロード
                              └─ 連携ファイル作成（export-definitions/*.json を参照）
```

## 5. 機能仕様詳細

### 5.1 マスタテーブル定義JSON（DO-1, DO-2関連）

配置場所: `table-definitions/{tableId}.json`

```json
{
  "tableId": "m_item",
  "tableName": "品目マスタ",
  "columns": [
    {
      "columnId": "item_code",
      "columnName": "品目コード",
      "dataType": "string",
      "maxLength": 20,
      "notNull": true,
      "unique": true,
      "primaryKey": true
    },
    {
      "columnId": "item_name",
      "columnName": "品目名",
      "dataType": "string",
      "maxLength": 100,
      "notNull": true,
      "unique": false
    },
    {
      "columnId": "item_type",
      "columnName": "品目区分",
      "dataType": "string",
      "maxLength": 10,
      "notNull": true,
      "unique": false,
      "constants": ["完成品", "半製品", "原材料"]
    },
    {
      "columnId": "safety_stock",
      "columnName": "安全在庫数",
      "dataType": "number",
      "notNull": false,
      "unique": false
    }
  ]
}
```

**フィールド定義**

| フィールド | 型 | 必須 | 説明 |
|-----------|-----|------|------|
| tableId | string | ○ | テーブルの一意識別子。IndexedDBのオブジェクトストア名として使用 |
| tableName | string | ○ | 画面表示用のテーブル名（日本語可） |
| columns | array | ○ | カラム定義の配列 |
| columns[].columnId | string | ○ | カラムの一意識別子（テーブル内） |
| columns[].columnName | string | ○ | 画面表示用のカラム名 |
| columns[].dataType | enum | ○ | `string` \| `number` \| `boolean` \| `date` のいずれか |
| columns[].maxLength | number | dataTypeがstringの場合のみ有効 | 最大文字数 |
| columns[].notNull | boolean | ○ | true の場合、値が空・null・undefinedであればエラー |
| columns[].unique | boolean | ○ | true の場合、テーブル内で値が重複していればエラー（単一カラムのみ） |
| columns[].primaryKey | boolean | いずれか1カラムに指定必須 | true の場合、自動的に notNull=true, unique=true として扱う。IndexedDBのkeyPathとして使用 |
| columns[].constants | array\<string\> | 任意 | 指定した場合、値がこのリストに含まれない場合エラー |

**制約条件（バリデーションエンジンが定義JSON自体をチェックする際のルール）**

- 1テーブル定義につき primaryKey=true のカラムはちょうど1つでなければならない
- primaryKey=true のカラムに notNull=false または unique=false が明示指定されている場合は、定義エラーとして起動時に警告を出す

### 5.2 バリデーションエンジン仕様（DO-4関連）

CSV取込時、各行・各セルに対して以下の順序でチェックを行う。

1. **型チェック**: dataTypeに従い値が変換可能か（例: numberなら数値変換できるか、dateなら日付として解釈できるか）
2. **NotNullチェック**: notNull=trueのカラムで値が空でないか
3. **長さチェック**: dataTypeがstringの場合、maxLengthを超えていないか
4. **定数チェック**: constantsが定義されている場合、値がリストに含まれるか
5. **ユニーク制約チェック**: unique=trueのカラムについて、（a）CSVファイル内での重複、（b）IndexedDB内の既存データとの重複、の両方をチェックする。ただしprimaryKeyと値が一致する既存レコードは重複エラーではなくUpsert対象として扱う（5.3参照）

いずれか1項目でもエラーの行は、その行のみ登録をスキップし、エラー内容を取込ログに記録する（DONT-1により、テーブル間の整合性チェックはこのバリデーションフローに含まれない）。

### 5.3 CSV取込処理仕様（DO-3関連）

- 取込単位: 1回の取込操作＝1CSVファイル＝1テーブル
- 処理方式: Web Workerでファイル読込・パース・バリデーションを実行し、メインスレッド（UI）をブロックしない
- 重複データの扱い: CSV内のレコードの主キーが、IndexedDB内の既存レコードの主キーと一致する場合、**Upsert（上書き更新）**する
- エラー時の扱い: バリデーションエラーが検出された行は**スキップし、正常な行のみ登録する**（部分成功を許容する。All or Nothingにはしない）
- 処理完了後、取込ログ（5.5参照）を1件生成する

### 5.4 連携ファイル作成機能仕様（DO-8関連）

配置場所: `export-definitions/{exportId}.json`

```json
{
  "exportId": "item_export_v1",
  "exportName": "品目マスタ連携ファイル",
  "sourceTableId": "m_item",
  "outputColumns": [
    { "sourceColumnId": "item_code", "outputHeader": "ITEM_CD" },
    { "sourceColumnId": "item_name", "outputHeader": "ITEM_NAME" },
    { "sourceColumnId": "item_type", "outputHeader": "ITEM_TYPE" }
  ],
  "fileFormat": {
    "delimiter": ",",
    "encoding": "UTF-8",
    "includeHeader": true,
    "lineEnding": "CRLF"
  }
}
```

- マスタ検索画面から、定義済みの連携ファイル仕様（exportId）を選択し、検索結果（または全件）をこの仕様に従ったファイル形式でダウンロードできる
- CSVダウンロード機能（DO-7、素の全カラム出力）とは別機能として扱う。DO-7は「今見ている検索結果をそのままCSVに」、DO-8は「決められた連携先フォーマットに変換して出力」という役割分担

### 5.5 取込実行ログ仕様（DO-9関連）

IndexedDB内に `import_logs` という管理用ストアを設け、取込1回につき1レコードを記録する。

```json
{
  "importId": "uuid-xxxx",
  "tableId": "m_item",
  "fileName": "item_master_20260830.csv",
  "startedAt": "2026-08-30T10:00:00Z",
  "finishedAt": "2026-08-30T10:00:03Z",
  "status": "COMPLETED_WITH_ERRORS",
  "totalRows": 100,
  "successRows": 95,
  "errorRows": 5,
  "errors": [
    { "rowNumber": 12, "columnId": "item_type", "message": "定数リストに含まれない値です: 資材" }
  ]
}
```

| フィールド | 説明 |
|-----------|------|
| status | `RUNNING` \| `COMPLETED`（全行成功） \| `COMPLETED_WITH_ERRORS`（部分成功） \| `FAILED`（処理自体が異常終了） |
| errors | エラー明細の配列。行番号・カラムID・エラーメッセージを記録する |

取込実行ログ画面では、この`import_logs`ストアを一覧表示し、任意の1件を選択してエラー明細を確認できるようにする。

## 7. 実装時の注意事項（ClaudeCodeへの申し送り）

1. 本書のセクション3「やらない事」に記載の機能は、要求が曖昧に見えても実装に含めないこと。疑問があれば実装を止めて確認すること。
2. EFFECT-1・EFFECT-2（セクション1.2）を満たしているかを、新規マスタテーブル追加のシナリオで動作確認すること。
3. マスタテーブル定義JSON（5.1）は、本書のサンプル（品目マスタ）以外に、最低1〜2種類の異なるテーブル定義（例: 取引先マスタ等、カラム構成が異なるもの）でも動作することを確認すること。単一のテーブル定義でしか動かない実装は、DAO実行時生成の検証として不十分である。
4. IndexedDBのスキーマ変更（テーブル定義JSONの追加）に伴うDBバージョンアップの扱いは、PoCでは簡易に「バージョン変更時は既存データを削除して再作成する」で構わない（本番相当のマイグレーション機構は不要、DONT-4に準ずる簡易方針）。
